## 方案对比与取舍

比较标准是：官方接口、在微信中使用、接入与运行尽量轻量、复用 QQChat 现有能力，并核对能否接入普通微信群。以下结论基于 2026-10-21 已查阅的公开资料；“未核实支持”不等于断言不存在未公开或灰度能力。

| 方案 | 已核实的会话边界与接入方式 | 取舍结论 |
|---|---|---|
| **iLink Bot API（选定）** | 腾讯官方插件公开了扫码、HTTP JSON 和长轮询协议；当前插件只声明 `direct` 私聊，普通微信群未核实支持 | 满足官方微信私聊入口，计划用 Python 直接接入并复用现有核心；接受当前没有群聊，账号资格与实际收发由 G0 验证 |
| 企业微信智能机器人 | 官方支持企业微信场景的私聊与群内 `@`，有 WebSocket 长连接和 Python SDK；无需公网回调地址 | 本身可以轻量接入，但会话入口属于企业微信，未查到能接入现有普通微信群的官方支持；本次不选择切换到企业微信场景 |
| 公众号 / 服务号消息接口 | 接收用户向公众账号发送的消息 | 需要在公众号 / 服务号会话中使用；“群发”是向订阅用户广播，不是参与普通微信群；本次不采用 |
| 微信客服 | 用户进入客服入口后，可通过 API 收发客服会话消息；有专属会话状态、发送窗口和条数限制 | 面向客服会话，不能据此获得普通微信群能力；本次不采用客服入口 |
| 企业微信消息推送（原“群机器人” webhook） | 通过 webhook 向对应群推送消息 | 单靠该接口不能接收群消息并完成机器人对话；不作为双向聊天方案 |
| 非官方桌面收发、Hook 或协议接入 | 部分路线声称可处理普通微信群，但依赖具体客户端、常驻桌面或非官方实现，未做账号实测 | 用户已因账号限制 / 封号风险明确放弃，不继续安装或验证，不作为 iLink 缺少群聊时的替代路径 |

### 选择 iLink 的理由与接受的限制

1. **采用官方微信私聊入口。** 不引入用户已拒绝的非官方群聊接入；其他官方接口各有用途，但不等价于普通微信机器人或普通微信群入口。
2. **保持接入轻量。** 依据官方公开协议，在现有 Python 项目中新增渠道适配和独立运行入口；不安装完整 OpenClaw，也不依赖长期在线的 Windows 微信客户端。已验证本账号的 Python 最小收发与重启、两分钟延迟；完整 G0 仍需指定附件格式证据。
3. **复用已有能力。** 延续同仓库双实例方案，共用人格、CCR 模型与工具，账号、当前会话和运行状态数据库分开；按 2026-10-22 新决定另设共享记忆与授权资料区，不复制整个 `wxChat` 项目。
4. **接受能力边界。** 微信渠道仅验收私聊；原生语音、任意时刻主动发送和普通微信群均不作承诺。公开字段中出现 `group_id` 不构成群聊支持证据；企业微信能力与微信客服的发送限制也不能套用到 iLink。

选型、最小收发及两分钟延迟已有证据，未覆盖的媒体格式和长期行为仍由后续任务验证。若 G0 无法通过，应记录具体阻碍并重新评估，不自动切换到非官方路线。只有官方明确开放相应群聊接口、且用户重新确认范围时，才另行制定群聊计划。

## 问题与目标

项目维护者希望在微信私聊中使用现有夏莉人格、CCR 模型与工具，并让夏莉在不同 QQ 群和微信私聊中保留连续记忆。当前 QQ / 微信均已服务器常驻；历史和文件按会话隔离，通过独立共享记忆库延续授权事实，单纯共享文件目录不会产生跨会话记忆。

目标是保留 `qqChat` 仓库与目录，在同一代码库内增加微信入口，独立启动 `wxchat-bot`。公共能力只维护一份；两端的凭证、当前会话、收件 / 任务数据库、私有工作区及运行备份分开，另设独立共享记忆存储和授权资料区。以可检索的长期记忆延续人物关系、偏好、项目事实和重要经历，并定期压缩；不把全部群聊与私聊拼成同一个上下文。既有 QQ 功能必须通过回归验收。

- 自动根据昵称合并身份、无范围共享全部原始聊天 / 私有文件、默认全量导入历史；跨端长期记忆与显式授权资料共享已纳入，原始会话记录仍分别管理。

## 已选方案与责任划分

### 一套代码、两个运行实例

```text
同一 qqChat 源码 / 构建产物（各容器可固定不同已验证版本）
  ├─ app.main → QQ Webhook / QQClient → qqchat-bot
  │                                      └─ 原有数据、工作区、备份
  └─ app.main_wechat → 微信长轮询 / WeChatClient → wxchat-bot
                                                 └─ 微信专用数据、工作区、备份

两实例各自使用公共对话、权限和工具代码
  ├─ 共享记忆模块 → 独立记忆库（身份、事实、来源、可见范围、修订）
  ├─ 授权资料模块 → 共享资料区（私有工作区仍各自保留）
  └─ 复用 CCR Fusion、搜索、图片适配与 B 站文本资料服务
```

新增入口建议为 `app/main_wechat.py`，微信实现收敛到 `app/wechat/`。QQ 原有入口、Webhook 路径和默认配置保持兼容。公共边界只覆盖现在确定的两渠道，不搬迁所有文件，也不新增插件注册机制。

### 消息、授权与能力

- 统一输入包含渠道、机器人账号、会话类型、会话键、可信发送者、显示名、消息 ID、命令正文、引用上下文、附件引用和是否明确对机器人发话。
- 命令正文与被引用内容分开，引用中的 `/reset` 等不能变成当前命令。附件来源标记保留，不能把机器人发出的表情误收为用户上传。
- 回复目标由传输层持有。`context_token`、下载签名和 AES key 只在渠道层 / 受保护状态中流转，不进入模型提示词、工具参数、普通日志或公开状态。
- 传输边界只需要文本发送、按类型发送本地文件、下载附件及明确的发送结果 / 错误。QQ 的 `msg_id/msg_seq` 留在 QQ 适配逻辑；微信使用稳定的 `client_id`。
- 微信每实例一个账号，只接受扫码确认返回的 `ilink_user_id` 对应用户；标识缺失或无法核实时拒绝绑定。不能把“第一个发消息的人”或昵称当管理员。
- 通过统一权限上下文向命令、工具和生成任务传递操作授权。微信绑定者可以管理自己的私聊和工作区；QQ 群主 / 管理员 / owner 原有行为用回归用例锁定，不顺便扩大权限。
- 能力随已验收渠道实现开放。M1 不触发表情发送、媒体工具或早安；M2 才开放通过验收的图片 / 文件能力；能力不可用时在入队和调用付费模型之前反馈。
- `persona.md` 保留唯一人格本体，将 QQ 场景语句迁入明确的渠道场景说明；帮助、状态、工具说明和上下文构造采用同一能力来源，避免口头承诺未实现功能。

### 共享长期记忆、压缩与资料（记忆与压缩已实现，授权资料共享延期）

**责任与范围。** 微信 / QQ 官方负责账号授权和消息传输；本项目负责身份映射、记忆保存 / 检索、压缩和权限。模型仅处理程序选择的当前对话与可见记忆，并协助提取 / 整理；模型输出不能自行修改身份绑定或扩大可见范围。当前请求是更新交接，不执行新功能开发。

| 层次 | 保留 / 共享方式 | 责任与验收 |
|---|---|---|
| 人格 | 同一份夏莉人格，渠道场景分别注入 | 复用现有 `persona.md`；事实记忆不改写系统人格或权限 |
| 当前上下文 | QQ 按群、微信按 `bot_account / peer` 保留最近对话 | 知道当前场景；不把其他群 / 私聊的原始记录拼进来 |
| 长期记忆 | QQ 群与微信私聊通过同一记忆模块读写事实、经历、关系与项目进度 | 每条有来源、时间、对象、可见范围和修订状态；先鉴权再检索，再给模型 |
| 文件 | 各会话私有工作区 + 独立授权资料区 | 维护者发布指定文件 / 版本并指定可见会话；目录共用不等于自动有权读取 |
| 运行状态 | QQ / 微信凭证、收件游标、任务、短期历史与恢复仍独立 | 不让一端重启 / 回滚处理另一端任务；共享记忆另行备份和恢复 |

**身份与第二帐号。** 首期仍是一个微信 Bot、一个可信扫码者及维护者现有 QQ 身份。将实际平台标识显式映射到同一内部人物，由维护者确认；不按昵称猜测，记忆里的“我是某人”也不能更改映射。未映射的群成员保持各自来源身份。当前扫码代码会拒绝将不同 Bot / 扫码者覆盖到既有本地绑定；这是本地行为，不保证服务端换号的影响。未来同一人的第二微信帐号可复用内部人物与授权记忆，但多帐号接入、换绑和服务端行为仍是后续扩展，不因本次方向确认而自动启用。

**连续记忆与可见范围。** 从授权会话的新消息增量提取有长期价值的事实，而非要求用户逐条复制笔记。维护者本人在 QQ 群提出的偏好 / 项目事实可沉淀为本人私有记忆，在确认身份的微信私聊继续使用；其他成员的信息默认留在来源会话，跨群可用的项目记忆须有明确共享范围。对群回复按整个目标会话的可见权限筛选，不能因为发问者是维护者就把其私聊资料提供给模型。常规查询先过滤权限再按主题 / 人物 / 时间检索，只注入有界的相关条目，引用来源；检索不到就说明，不凭空补记忆。

**保存、纠正与遗忘。** 一份独立记忆存储为事实、来源和当前修订的唯一依据；记录稳定 ID、来源会话 / 事件、人物、事实发生与记录时间、事实 / 待核实状态、可见范围和版本。模型推断不能直接成为已确认事实；聊天内容中的指令不能改权限、覆盖人格或执行工具。提供维护者可用的查看、纠正、遗忘与共享范围管理入口，复用现有命令 / 受控维护操作，不新增管理站。`/reset` 只重置当前短期对话；删除长期记忆是独立、范围明确的操作。纠正或遗忘需同步使旧摘要 / 索引失效，恢复备份时保留删除依据，不能让已删除记忆自动复活。

**定期压缩。** 必须有可配置周期任务，实施初值为每日检查一次（Asia/Shanghai，具体时段结合维护窗口），容量阈值可额外触发，不能以“满了再处理”替代定期整理。仅整理新增 / 变化部分，合并重复项、压缩冗长叙述，保留关键事实、来源、时间、人物和可见范围；不同权限范围分别处理，不能把私聊摘要升级为全局可读。关联的重要证据片段按受控保留策略保存，避免只反复压缩上一版摘要而失真，也不承诺永久保存全部原始聊天。旧版保留受限恢复窗口；定稿后事务切换版本，失败或中断保留旧版。压缩前发生的并发纠正 / 删除必须被检测，不能用旧快照覆盖。限定模型调用成本、输入大小和批量；无更新不调用模型，不发送主动微信消息。

**最小实现与维护边界。** 沿用同机双实例，优先通过一个共用模块访问独立的本地 SQLite 记忆库，先做结构化 / 关键词检索，暂不引入向量数据库、Redis 或中央机器人服务；检索质量由跨端场景验收，不预设必须上新基础设施。写入使用短事务与有界冲突重试，压缩生成在事务外，提交时校验版本。周期压缩由指定维护实例负责并持有跨进程锁，防止两端重复整理；共享目录 / 记忆库不放进任一端自动清理范围，也不使用不适合 SQLite 的网络文件系统。若以后跨主机部署，再评估访问方式。

**资料共享与恢复。** 首期仅维护者可发布 / 撤销共享资料，沿用限大小、路径和符号链接防护；以受控复制 / 版本化发布保存指定文件，私有原件不随之开放。读取和发送前都检查授权；模型不能直接访问共享根目录绕过检查。共享数据单独备份；禁用共享功能可退回各自短期对话，不能顺手删除记忆。运行实例单独回滚不回退共享库；确需恢复共享数据时，先协调两端停止共享读写，再按版本和删除记录恢复。

**交付顺序。** G0 → M1 → M2 → GM（T-014～T-017）→ M3（原 T-013）。T-005 / T-006 预留可信身份、来源、当前会话与记忆注入边界，但共享记忆在 B5 验收后才启用。GM 先用候选环境的两渠道事件联调及微信试用验证，生产 QQ 切换后的真实跨端连续性在 T-013 验收，避免为验证记忆提前改动旧 QQ。验收至少覆盖 QQ 本人项目事实转到微信继续、获准跨群检索、私聊资料不进入群模型输入、压缩前后事实 / 权限一致、纠正 / 删除不复活、共享文件撤销、并发写入与故障恢复。

### 数据、游标与失败恢复

1. QQ 原有库、路径和群键保持兼容。微信使用独立库，微信会话键按 `wechat / bot_account / peer` 生成，事件去重键包含机器人账号和原始消息 ID。ID 按字符串无损保存。
2. 微信 Bot 登录凭证存放在专用数据卷的受限文件，原子写入；回复令牌、游标及微信收件记录落微信 SQLite，不另建同步服务。备份同样按敏感资料保护。
3. 微信增加最小的收件持久记录和渠道状态记录，仅在微信库初始化。每批消息去重入库、相应回复上下文与新游标在同一事务提交；失败则不推进游标。未授权消息不保存正文，可记录拒绝计数。
4. 单个轮询器加有界处理队列；处理模型请求不能阻塞下一轮收件。积压达到持久化容量上限时暂停拉取并显示 degraded，恢复容量后继续；限制不能只放在内存队列。
5. 本机最小实现由 `wx_inbox` 同时记录等待 / 执行 / 终态，`wx_outbox` 按请求关联发送；直接等待共用处理器完成，不再套用 QQ 内存任务队列，因此没有第二份微信 `task_runs` 真相源。后续复杂调度如需拆分，应另行验证一致性；已有长任务不能绕过微信收件终态记录。
6. 只有未开始的持久待处理消息可以在重启后恢复执行。已执行或执行状态不确定的写文件、生图等任务不自动重跑；记录中断，当前先使用原入站上下文尝试一次提示；上下文已过期时提示可能失败，下一有效入站汇总仍待补齐。按需重新发起，不自动重做。
7. 发出前确定回复序号与稳定 `client_id`，保存可关联状态；检查 HTTP 和业务返回码。超时等结果不明时记 `delivery_unknown`，不能换 ID 盲目补发或宣称成功。未验证服务端幂等前，不承诺 exactly-once；明确未发出和结果不明要分开。
8. 普通读取 / 轮询对瞬时失败做有界退避；鉴权失效（包括 `-14`）进入需重新登录状态并停止高频重试。重登核对账号，避免把旧游标、令牌或待发任务交给另一个账号。
9. 微信重启恢复只记本实例未完成任务；不复用 QQ 启动时无上下文立即发通知的方式。通知发送失败保留未送达状态，不循环刷屏；下一次有效私聊汇总仍是 T-007 剩余项。

保留这两类持久记录是为了防止“游标已推进但消息尚未处理”以及“重启重复执行工具”的具体故障，不引入通用队列、中央状态服务或另一份聊天历史。

### 协议与媒体实现约束

- 首先按发布包复现 `POST get_bot_qrcode?bot_type=3`、二维码状态 GET、`POST getupdates/sendmessage`；公共请求头和 `base_info` 按操作构造，不能假设只填 Bearer 即可。
- 本项目自行实现 Python 渠道适配，依据腾讯公开协议与官方插件；不把它称为腾讯官方 Python SDK。插件使用的 `iLink-App-Id=bot` 是公共应用标识，不是需要用户提供的 AppSecret；`bot_agent` 使用本项目实际版本标识，鉴权使用扫码返回的 Bot token。服务端是否接受该实现由 G0 验证。
- 登录需处理等待、扫码、过期、验证码、验证失败、重定向与已绑定状态；CLI 展示可扫码二维码，用户无需手抄令牌。若需要二维码渲染依赖，固定版本并记录用途。
- 使用登录响应的有效 API 地址；校验 HTTPS、主机和重定向，拒绝内网 / 本机和未经核实的域名。正式支持的腾讯域名在 G0 根据资料与响应确定，不能为通过测试放开任意 URL，也不能向 CDN 携带 Bot Authorization。
- 默认 API 为 `https://ilinkai.weixin.qq.com`，默认 CDN 为 `https://novac2c.cdn.weixin.qq.com/c2c`。优先采用经校验的服务端完整媒体 URL，必要时兼容查询参数形式。
- 复用现有 `cryptography` 实现协议指定的 AES-128-ECB / PKCS#7；兼容已知 key 编码。入站下载流式限大小，解密、校验后才进入工作区；出站加密上传后以业务消息发送。
- 保留工作区路径、符号链接、文件大小和容量防护；上传失败与消息发送失败分别记录。图片说明和媒体分次发送时区分各自结果，不能把部分成功计为全部完成。
- 引用消息有内容时直接规范化；只有服务器消息 ID 时从本账号、本会话的已保存记录解析。找不到就说明上下文不可用，不跨会话寻找。优先复用微信收件、聊天和已发媒体记录，不新建引用缓存服务。

### 部署与资源

- 在现有 Compose 中给微信增加可选 profile，避免原有启动命令自动启动未配置的微信服务。微信启动只选择自身服务，不执行整个项目的 `down`，不重建或重启 QQ 及共享依赖。
- 两实例使用独立 env、运行数据 / 私有工作区 / 备份挂载；微信不挂载 QQ 私有数据，反向同样隔离。共享记忆和授权资料另设显式挂载及独立备份，不嵌入任一端的自动清理目录；相关身份与来源按敏感信息管理。
- 微信只需出站连接，首版不新增公网端口；保留容器内部健康接口供 Docker 探测，运行时区分进程存活、账号就绪、最近成功轮询和积压，不把“未收到新消息”当掉线。
- 共用构建定义但按发布版本固定镜像，微信可先运行新版本，QQ 可继续保留旧镜像。人格等只读资源也应按部署版本提供，避免修改同一宿主文件立即影响线上 QQ。
- 沿用非 root、只读根文件系统、有限 tmpfs、日志轮转与进程限制。微信首版工具 worker 取 1，QQ 现有配置不改；资源预算在本地构建 / 试用阶段实测后确定，不直接把两边所有限额翻倍。
- 搜索和 CCR 复用现有服务；独立凭证只有在现有服务已支持时才采用。图片 / 语音适配器目前与既有客户端 Key 绑定，不能假设换一个新 CCR Key 就能调用它们；本计划不扩展凭证系统。
- 两实例共用上游配额，进程内信号量不代表全服务器并发。M2 并发试用核对 CCR / 辅助服务容量；重型 B 站成片分析与微信语音暂不启用，避免把跨进程调度系统带入首版。
- 新增微信 env、登录资料与媒体临时目录时同步核查 Git / Docker 忽略规则；构建上下文不得上传这些资料。只改 `.gitignore` 不能替代 `.dockerignore`。
